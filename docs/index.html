Community project, shared as-is.

This site documents a community reference implementation and the evidence gathered from it. It is not a Microsoft product, is not supported by Microsoft and does not come with an SLA or warranty.

Before importing anything: test in a non-production environment first, get your organisation's approvals, review the solution contents, configure your own connections and storage, and decide whether the approach is appropriate for environments that hold real data.

The MIT licence permits reuse, but it does not provide support, fitness guarantees, security approval, production readiness or rights to excluded templates and private comparison files. You are responsible for assessing, operating and securing anything you deploy from this site.

Architecture

Prepared templates are explicit contracts.

The documented Standard route separates drafting, rendering and review. The comparison cases remain useful, but they are not interchangeable with a deployed, configured Standard implementation.

01 / Results and readiness

Different routes. Different proof.

The original request was for the Standard harness, not the GitHub Copilot harness (GHCP). Later attachment-driven comparisons are separate experiments, not replacements for that requirement.

Can I use my own Word template?

Yes, after a maker prepares it. This working implementation accepts a new subject, context and requested content for a previously prepared Word layout. It is not a one-step “upload any DOCX and follow its layout” route. New content is dynamic; a new design is setup/engineering work. See the template onboarding steps.

This describes the integration demonstrated here, not a product-wide restriction on Standard harness agents. The original ad-hoc Word comparison is a separate experiment, not proof that the prepared flow accepts arbitrary templates.

03 / Reuse the approach, not the tenant

A template is an integration contract.

Conversation, research and revision logic can be reused. Each design still needs its own destinations, bounds, flow/topic bindings and quality review.

  1. Prepare the template contract. Add supported controls or mapped slide fields, freeze the file version and record the required template boundaries.
  2. Bind the environment. Configure destination connections, OneDrive folders, prompt settings and file IDs in the maker designer.
  3. Validate before activation. Test with synthetic data, preserve failed attempts and activate only the intended, fully configured routes.
  4. Review the output. Check factual accuracy, layout, editability, placeholders, governance and access before any real use.

Prepared Word

New content uses a prepared layout. To use a different organisational Word template in this implementation, a maker must first:

  1. Add supported, uniquely named content controls in Word's Developer tab, with repeating sections and named nested controls for dynamic table rows.
  2. Align the saved prompt's drafting schema and row-object keys with the flow's population mappings.
  3. Store and configure the exact template/version in the flow. Selecting that file in Populate a Microsoft Word template exposes its control schema; map fields and repeating-row arrays to it.
  4. Validate required fields and rows, then human-review rendered pages and a marked editable copy before accepting the new design.

See Microsoft's Word Online (Business) template and repeating-section guidance. Once that setup is complete, bind new authorised source notes to the saved drafting prompt. Validate narrative fields and typed table rows, add trusted application-owned date/version values, obtain creation consent for the reviewed draft and populate the prepared controls through Power Automate.

Compare actual output text, table rows, static headings, styles, headers and footers with the intended content. Native rendering and edit/save/reopen check things schema validation cannot. New content is dynamic; a new design is setup/engineering work, not a one-step upload-any-DOCX operation.

Prepared PowerPoint

Register the exact template version and map editable shapes and paragraphs. Keep generation within explicit field bounds, validate before rendering and transfer accepted text without silent truncation or repairs.

For a slide revision, retain the successful full draft and source file. Merge only the requested slide and notes after validation; return a new file. Failed validation must not replace the last successful state.

Human review is part of the workflow. Evaluate factual accuracy, completeness, readability, editability and data governance independently. Neither structural preservation nor file delivery certifies production readiness, compliance or approval.

Image handling and channel qualifications

The local design validates actual image bytes: one nonanimated JPG or PNG, up to 5 MiB, 20 megapixels and 10,000 pixels per side. It fits the whole oriented image without stretching or cropping; deterministic resizing and pale letterboxing produce a PNG. This is not AI-generated imagery or byte-identical embedding.

Private retention and exact-version reuse for revisions are designed but unproved in the rejected native renderer. Uploads require a supported channel; the SharePoint agent channel does not support these uploads. Storing a generated presentation in SharePoint is a separate capability. See Microsoft's file-input guidance.

Practical onboarding checklist
  1. Confirm template ownership, redistribution rights, permission and authorised source context before any processing.
  2. Freeze a version and record its hash. Map Word controls or PPT shape/paragraph destinations; define required keys and per-field/row limits.
  3. Keep research queries separate from private context. Treat retrieved content as evidence, not executable instructions.
  4. Bind prompts and flows in your own environment. Configure least-privilege connections, consent, file ownership, retention and error handling.
  5. Validate native activation and topic types, then test creation, missing inputs, refusal, validation failures and isolated revisions with synthetic data.
  6. Review every rendered page or slide, check placeholder removal and factual grounding, and verify a marked copy can edit/save/reopen. Retain immutable originals and failed attempts.

The separately listed native solution ZIP includes the as-deployed Standard agents, flows and prompt configurations, with source-specific setup metadata but no live connections. Download availability is not tested cross-tenant installation; follow the native solution setup guide before any activation.
